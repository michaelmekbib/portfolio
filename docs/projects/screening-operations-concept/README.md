# One Passenger One Record

**A proposed integrated screening-operations capability in 1CDP for outbreak response at ports of entry.**

**Status:** Innovation concept and recommendation under review; implementation proposed  
**My role:** Response workflow observation, informatics analysis, concept development, and innovation pitch  
**Context:** 2026 Ebola response at Washington Dulles

## The operational problem

Staff reconciled passenger manifests, spreadsheets, screening records, and schedules across separate tools. Repeated entry of demographic and flight information created avoidable handoffs, version conflicts, reconciliation work, and repeated handling of personal information.

## The proposed capability

The design follows an “enter once and reuse” principle within an integrated operational layer:

| Workflow stage | Proposed capability |
| --- | --- |
| Import | Validate incoming manifests and manage versions. |
| Assign | Generate port and flight worklists. |
| Screen | Pre-populate known passenger and flight details for assessments. |
| Resolve | Match status and route duplicate, incomplete, inconsistent, or unmatched records for review. |
| Monitor | Link response records and show progress, referrals, exceptions, and staffing coverage. |

Deployer scheduling, role-based views, and configurable disease and location rules are part of the proposed reusable capability. QARS linkage is a proposed integration, not a completed connection.

## Expected value and evaluation

The pitch anticipates faster assessments, fewer transcription corrections, earlier escalation, and a shared operational view. These are expected benefits; the supplied material does not establish measured deployment outcomes.

Proposed success measures include time to a validated worklist, time to the first assessment question, automatic match rate, exception rate, and staffing visibility.

## Proposed implementation path

Discovery and design would precede an MVP, a Washington Dulles pilot, and enterprise hardening. The presentation estimates approximately **4–6 months** for an initial capability, subject to architecture, integration, authorization, and roadmap dependencies. This is a proposal estimate, not an approved delivery commitment.
